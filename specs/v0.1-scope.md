## 1. Goal
Deliver a **clean, tested, working first version** of the platform's core engine:
**organization hierarchy + form builder + workflow engine**.

Prove the platform is **generic** by building two very different business processes, an HR leave
approval and an NBFC loan approval, **using only configuration** (no code changes).

"Not a proof of concept" means: real architecture, real database with migrations, real login,
automated tests and a setup guide. The **features** are limited; the **quality** is not.

## 2. Users (personas)
| Persona | What they do in v0.1 |
|---|---|
| **Platform Admin** | Manages the org hierarchy, users and roles; handles stuck tasks |
| **App Designer** | Builds apps, forms and processes, and publishes them |
| **Requester** | Starts a request by filling a form, tracks it, and fixes it when it is sent back |
| **Approver** | Works on tasks in the inbox: approves, rejects or sends back |

One person can have more than one persona.

### 3.2 Organization hierarchy (ORG)
| ID | Feature |
|---|---|
| ORG-01 | Admin defines **unit types** with their own names (e.g. Head Office, Zone, Branch; or Hospital, Department) |
| ORG-02 | Admin builds a **tree of org units of any depth**: create, rename, move, deactivate. A unit cannot be moved under itself or its own children |
| ORG-03 | Each unit has a type, a unique code, a name and an optional **head** (a user) |
| ORG-04 | Each user belongs to one **primary unit** and may have a **reporting manager**. No reporting loops (a user can't be their own manager, directly or through a chain) |
| ORG-05 | Admin defines **business roles** (e.g. Credit Officer, HR Officer) and assigns users to them |
| ORG-06 | **Approver rules** that the workflow engine uses to find who should act. See the list below |
| ORG-07 | Admin can **test a rule**: choose a requester and see who the rule resolves to. **Moved to v0.2** (G1) |

**ORG-06 approver rules:**
| Rule | Example |
|---|---|
| a. Specific user | "Priya" |
| b. The requester | Requester fixes their own request |
| c. Requester's manager, **N levels up** | Manager (N=1), manager's manager (N=2) |
| d. Head of the requester's unit | Branch Manager of the requester's branch |
| e. Head of the **nearest unit at or above** the requester's unit with **type T** | Zonal Head of the requester's zone |
| f. Users with **business role R**, anywhere or only **inside a unit relative to the requester** (including the units below it) | Credit Officers in the requester's zone |
| g. The user chosen in a **user-picker field** of the form | "Select your reviewer" |

**Detailed rules** (vacant heads, self-approval, empty results, codes, deactivation) and draft acceptance

### 3.3 Apps and versions (APP)
The **whole app** (all its forms and processes together) is versioned as one unit, like Joget. This
avoids mismatches such as a process using a field that a newer form version removed. (Decisions Q8.1–Q8.5.)

| ID | Feature |
|---|---|
| APP-01 | App Designer creates an **app**, a container that groups forms and processes: name, code, description |
| APP-02 | **App versions:** Draft → Published. Publishing freezes all forms and processes of the app together. A published version never changes; editing starts a new draft copied from a chosen version |
| APP-03 | **Active version:** the designer chooses which published version is active. New requests use the active version. Choosing an older version is a **rollback** |
| APP-04 | **Running requests** stay on the version they started with, unless an admin restarts them on another version (APP-05). Form-only changes therefore reach only new (or restarted) requests |
| APP-05 | **Restart on a new version** (Platform Admin). For one or several running requests, the admin restarts them on the **active version** and must enter a reason. Open tasks are cancelled and the request goes back to the **requester at the start**, using the **target version's form**: values are copied by field key, new fields start empty (or with their default), and removed fields are no longer shown but their old values stay in the history. The requester reviews, fills new fields and resubmits; the request then follows the **target version's flow from the first step**. The request number and history are kept; the history shows who restarted it, when, why and on which version. The requester gets an email. Until resubmitted, the request shows as **Waiting for resubmission**; from v0.2 the requester can also withdraw it (WF-10) |
| APP-06 | Approvers are found **when each task is created**, using the org data at that moment. Tasks that already exist keep their assignee; an admin can reassign them |
| APP-07 | An app can be **disabled**: its processes disappear from "Start a request", and running requests continue. It can be enabled again. Apps are never deleted |

**Detailed rules** (one draft at a time, publish note, restart type conversion, concurrency) and draft
acceptance criteria: [docs/discussions/apps-and-versions.md](../docs/discussions/apps-and-versions.md), decided by the owner (A1–A10).

### 3.4 Form builder (FRM)
| ID | Feature |
|---|---|
| FRM-02 | **Drag-and-drop** form designer with live preview |
| FRM-03 | Field types: Text, Text area, Number, Currency, Date, Dropdown, Radio buttons, Checkboxes, Yes/No, Email, File upload, User picker, Calculated (read-only), **Grid** (FRM-13). Layout items: **Tabs**, Section (with title), Label/help text |
| FRM-04 | Field properties: label, unique key, **data type** (Text, Whole number, Decimal, Date, Yes/No; allowed list per control), help text, default value, required, read-only. A key keeps one type family in all versions |
| FRM-05 | Validation: min/max length, min/max value, pattern, and **cross-field rules** written as expressions (e.g. `ToDate >= FromDate`) with a custom message shown under a chosen field or at the top. **"Required when"** expressions; rules can be limited to chosen workflow steps. Runs in the browser **and** on the server; the server decides. Runs on Submit, Resubmit and Approve only |
| FRM-06 | **Calculated fields** use the expression language. A calculated field may use other calculated fields; **loops are rejected** when the design is saved |
| FRM-07 | **Show/hide rules:** a field or section is visible only when an expression is true. Hidden fields are not validated and their values are not saved |
| FRM-08 | Forms are versioned as part of their app (APP-02); there are no separate form versions |
| FRM-09 | Form data is saved with the app version used to enter it |
| FRM-11 | Every change to form data publishes a **`FormDataSaved`** event in the same transaction: record ID, form, app version, a data version that increases by 1 per change, and a full snapshot of the values (prepares for the read copy in [ADR-0002](../docs/decisions/0002-form-data-original-and-read-copy.md)) |
| FRM-10 | File upload: **multiple files per field**; maximum number of files, maximum size per file and allowed file types per field. Files are stored through a storage interface (local disk in v0.1) |
| FRM-12 | **Layout:** per section the designer chooses 1–4 fields per row and labels left or above; a form can be divided into **tabs** (with show/hide rules and error counts) |
| FRM-13 | **Grid:** a table inside the form where the user adds, edits and deletes rows; row-level calculated columns; `SUM`/`COUNT` over a grid; per step hidden, **view-only** (the "Datalist view" of the owner's request) or editable |
| FRM-14 | **Step-wise saving:** each workflow step saves only the fields it may edit; parallel branches never share an editable field ([ADR-0003](../docs/decisions/0003-form-data-storage-layers.md)) |

**Detailed rules** (keys, patterns, defaults, files, grid, tabs) and draft acceptance criteria:
[docs/discussions/form-builder.md](../docs/discussions/form-builder.md), decided by the owner (F1–F10, G1, G3, S1–S3).

### 3.5 Expression language (EXP), shared by forms and workflow
| ID | Feature |
|---|---|
| EXP-01 | Values: numbers, text, true/false, dates, and field references (by field key) |
| EXP-02 | Operators: `+ - * / ^`, comparisons (`= != < <= > >=`), `and`, `or`, `not`, parentheses |
| EXP-03 | Functions: `DAYS_BETWEEN`, `YEARS_BETWEEN` (completed years, e.g. age), `TODAY` (installation time zone), `ROUND` (half away from zero), `MIN`, `MAX`, `IF`, `ISBLANK`, `CONTAINS` (multi-select fields), `SUM` and `COUNT` (over a grid, FRM-13) |
| EXP-04 | Expressions are checked when a design is saved (syntax, unknown fields, wrong types), with clear messages |
| EXP-05 | The same expression gives the **same result in the browser and on the server**, proven by one shared set of test cases |
| EXP-06 | Expressions cannot run code or access files, network or database |
| EXP-07 | **Blank values pass through:** maths or comparisons with an empty field (or division by zero) give blank. A blank show/hide rule hides, a blank validation rule passes, a blank Condition branch is not taken |

**Detailed rules** (decimal arithmetic, case-insensitivity, operators, functions) and draft acceptance
criteria: [docs/discussions/expression-language.md](../docs/discussions/expression-language.md), decided by the owner (E1–E12).

### 3.6 Workflow engine (WF)
| ID | Feature |
|---|---|
| WF-01 | **Visual process designer**: drag-and-drop nodes and arrows |
| WF-02 | Node types: **Start** (linked to a start form), **Approval** (human task), **Condition** (branches checked in the designer's order; the first true one is taken, otherwise the default path), **Parallel split** and **Parallel join**, **Notification** (email), **End** (outcome: Approved, Rejected or Completed) |
| WF-03 | Each Approval node has: a name, an approver rule (ORG-06), an **approval mode** (WF-14), the **maker-checker** tick (WF-15), allowed actions (Approve, Reject, Reject (final), Send back), whether a comment is required for Reject/Send back, which form fields (and grids) the approver can see, edit or must fill ("required at this step"), and whether to email new tasks to assignees |
| WF-04 | **Checks before publishing:** exactly one Start; at least one End; every node reachable from Start; every node can reach an End; every Condition has a default path; every Parallel split has a matching join; no loops in the diagram; parallel branches never share an editable field; "All must approve" steps have no editable fields. Each error points to its node |
| WF-05 | Processes are versioned as part of their app (APP-02 to APP-05); there are no separate process versions |
| WF-06 | **Start permission:** the designer chooses which business roles and/or org units may start the process |
| WF-07 | **Task assignment:** when a request reaches an Approval node, the approver rule is resolved using the org data at that moment (APP-06). One user: the task is assigned to them. Several users: depends on the approval mode (WF-14); in "Any one" mode it is offered to all of them, the first to **claim** it owns it, and a claimant can **release** it. Nobody: it goes to an **Unassigned** queue where a Platform Admin reassigns it. If the directory (Identity) cannot be reached, the action fails cleanly and the user is asked to retry |
| WF-08 | **Actions.** *Approve*: the request moves on. *Reject*: the whole request ends as Rejected and open parallel tasks are cancelled (it may be reopened, see WF-13). *Reject (final)*: the same, but the request can **never** be reopened. *Send back*: the request returns to the requester to edit and resubmit, then comes back to the same Approval node (inside a parallel section: the other branches' tasks are cancelled and, after resubmission, the request returns to the split). Reject, Reject (final) and Send back **do not validate or save field changes**; only the comment is kept |
| WF-09 | **Parallel:** the join continues only when all branches have finished |
| WF-10 | The requester can **withdraw** an unfinished request. **Moved to v0.2** (G1) |
| WF-11 | **History:** every action is recorded: who, what, when, comment, and the old and new values of changed fields |
| WF-12 | If two people act on the same task at the same time, only the first succeeds; the second sees a clear message |
| WF-13 | **Reopen:** if the designer allows it for the process, the requester can reopen a rejected request, edit it and resubmit it. It keeps the same request number, its full history and its app version. After resubmitting, it **restarts from the first step**, so all approvals happen again. There is no limit on how many times. A request rejected with *Reject (final)* cannot be reopened |
| WF-14 | **Approval mode** per Approval node: **Any one** (offered to all; first claim decides) or **All must approve** (one task per person; moves on when all approve; any Reject ends the request; any Send back means everyone approves again after resubmission; fields are view-only) |
| WF-15 | **Maker-checker:** per Approval node, "Must be a different person from earlier approvers", **on by default**. If nobody remains, the task goes to the Unassigned queue |

**Detailed rules** (statuses, "All must approve" details, send back in parallel sections) and draft acceptance
criteria: [docs/discussions/workflow-engine.md](../docs/discussions/workflow-engine.md), decided by the owner (W1–W10).

## 4. Reference scenarios (platform acceptance tests)
These scenarios are **configuration only**. If one of them needs a code change in the platform, a generic
feature is missing, so we fix the platform, not the scenario.

### RS-1: HR leave approval (complete)
**Org setup:** Company → Departments. Every employee has a reporting manager. Business role: *HR Officer*.

**Form "Leave Request":**
| Field | Type | Rules |
|---|---|---|
| Leave type | Dropdown: Casual, Sick, Earned | Required |
| From date | Date | Required |
| To date | Date | Required; must be on or after From date |
| Number of days | Calculated | `DAYS_BETWEEN(FromDate, ToDate) + 1` |
| Reason | Text area | Required, maximum 500 characters |
| Medical certificate | File upload | Shown and required only when Leave type = Sick and Number of days > 2 |

**Process:**
1. The employee submits the form.
2. **Approval** by the requester's manager (rule c, N=1). Allowed: Approve, Reject, Send back.
3. **Condition:** if Number of days > 10, then **Approval** by role *HR Officer* (rule f). Otherwise skip to step 4.
4. **End:** Approved. The requester is emailed automatically (NTF-04).

**Covers:** calculated fields, show/hide, cross-field validation, manager rule, role rule, condition, send back, reject.

### RS-2: NBFC loan approval (simplified)
**Org setup:** Head Office → Zones → Branches. Business roles: *Loan Officer*, *Credit Officer*, *Legal Officer*, *Valuer*. Every branch and zone has a head.

**Form "Loan Application":**
| Field | Type | Rules |
|---|---|---|
| Applicant name | Text | Required |
| Applicant mobile | Text | Required, 10 digits |
| Applicant email | Email | Required |
| Monthly income | Currency | Required, more than 0 |
| Loan amount | Currency | Required, 50,000 to 5,00,00,000 |
| Tenure (months) | Number | Required, 6 to 360 |
| Annual interest rate (%) | Number | Required, 1 to 36 |
| EMI | Calculated | `P * r * (1 + r) ^ n / ((1 + r) ^ n - 1)`, where P = loan amount, r = annual rate / 12 / 100, n = tenure |
| EMI to income (%) | Calculated | `EMI / MonthlyIncome * 100`; must be 60 or less, with the message "EMI is too high for this income" |
| KYC documents | File upload | Required |
| Property documents | File upload | Required |

**Process:**
1. The Loan Officer (at a branch) submits the application.
2. **Approval** by the head of the requester's unit, i.e. the Branch Manager (rule d). Can send back.
3. **Parallel split**, all in the requester's zone (rule f):
   - Credit check by *Credit Officer*
   - Legal check by *Legal Officer*
   - Valuation by *Valuer*
4. **Parallel join**
5. **Condition:**
   - Loan amount up to 10,00,000: **Approval** by the Branch head (rule d)
   - Above 10,00,000: **Approval** by the nearest **Zone** head (rule e)
6. **Notification** to the applicant's email field: "Your loan is sanctioned" (NTF-02).
7. **End:** Approved.

**Covers:** complex calculation (EMI), unit-head rule, ancestor-by-type rule, role-in-unit rule, parallel split/join, amount-based routing, notification to a form field, claiming tasks offered to several users.

**Not covered in v0.1:** credit bureau check, authority matrix, disbursement, sanction letter PDF.

requests and doctor calendars, so it comes in a later version.

## 6. Non-functional requirements (NFR)
| ID | Requirement |
|---|---|
| NFR-01 | **Security:** only a task's assignee (or claimant) can act on it. Only the requester, people who worked on the request, and admins can view a request. Designers' screens need the App Designer role; directory screens need Platform Admin |
| NFR-02 | **Performance**, on a developer machine with 10,000 requests and 50,000 tasks: the inbox loads in under 1 second, and a task action completes in under 1 second (excluding email delivery) |
| NFR-03 | **Reliability:** no lost events (outbox); handling the same event twice is safe |
| NFR-04 | **Portability:** runs on SQL Server 2019 or later; no Azure-only services; runs on Windows without Docker |
| NFR-05 | **Time:** stored in UTC and shown in the user's local time. Date-only fields have no time part |
| NFR-06 | **Browsers:** latest Chrome, Edge and Firefox. Built for desktop; usable on a tablet. **Amended 2026-10-23 (UI-05):** the frame, login and the screens of spec 007 are also usable on a phone (375 px) |
| NFR-07 | **Privacy:** no form values or other personal data in logs, errors or telemetry (constitution 11.2) |
| NFR-08 | **No hard delete:** deleting a business record only marks it as deleted (constitution 8.6) |
| NFR-09 | **Design format version:** every saved app, form and process stores its format version (constitution 8.7) |
| NFR-10 | **Languages:** all screen text comes from translation files; English only in v0.1; dates, numbers and currency formatted by locale (constitution 12.1) |
| NFR-11 | **Accessibility basics:** all screens usable with the keyboard; every form field has a label (constitution 12.2) |
| NFR-12 | **Coverage:** at least 80% line coverage for Domain and Application code (constitution 5.6) |

## 7. Definition of done
Each milestone (section 8) is done when **all** of these are true for the items in that milestone:
- [ ] M1: RS-1 and RS-2 are built through the UI only and run end to end, shown in a demo and covered by end-to-end tests. M2: the extended RS-2 (co-applicants grid, "All must approve" committee) does the same.
- [ ] Every feature ID in the milestone has acceptance criteria in its module spec, and every criterion has a passing automated test that names it.
- [ ] The expression test cases pass in both C# and TypeScript (EXP-05).
- [ ] No business-domain words appear in platform code (only in demo data and end-to-end tests).
- [ ] A fresh machine can be set up from the README in under 30 minutes.
- [ ] All tests pass, with no known critical bugs.

## 8. Milestones (approved 2026-10-21, SC1)
The decided scope is about 20–25 focused build days, so it is built in three milestones, each ending with a
